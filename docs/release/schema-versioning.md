# 版本化迁移

## 基础引擎

`pkg/schema` 提供严格连续的版本清单、校验和、数据库级互斥及持久执行记录。`Migrate` 独占一个物理连接，在同连接执行 GET_LOCK、写入 started 意图、DDL和最终状态；锁基于当前数据库名，必须直连同一个MySQL primary。该锁不提供多写节点集群级互斥。

MySQL DDL可能隐式提交，不能声明事务回滚。回调报错或panic会记录failed；进程/连接中断可能留下started。任何非applied状态都会阻止后续自动迁移和Verify，不能自动重跑部分执行的版本。操作结果或解锁回执丢失时返回不确定错误，并丢弃可能仍持锁的物理连接。引擎不输出底层SQL、连接凭据或panic原文。

`Verify` 只有有界SELECT，缺记录、待迁移、源码漂移、未来版本或脏状态均拒绝通过；它验证版本历史，不检测任意手工表结构漂移。迁移回调必须只用给定连接，不自行开事务、关闭连接或转到其他数据库；实际实现及其模型/SQL必须包含在不可变校验依据中。`SQLMigration` 将有序SQL和执行内容绑定，调用者必须提供真实迁移清单。

运行角色只能读取ledger；单独迁移角色执行DDL及记录迁移结果。权限分离测试已验证SELECT-only角色可以Verify但不能Migrate；实际部署GRANT、应用启动Verify与显式CLI还在后续阶段，当前不能把引擎包单独视为应用已完成版本化迁移。

## 已验证范围

纯单测涵盖清单顺序/缺口、checksum边界、历史漂移、脏状态与异常脱敏。integration测试自行创建带唯一标签的MySQL8.4.11容器及数据库，验证顺序执行、幂等、并发互斥、迁移中Verify阻断、只读运行角色、DDL部分提交、杀死自身迁移连接及DDL后panic；只回收核对标签后的自有容器/卷，不使用已有服务或任意外部DSN。

```sh
go test -race ./pkg/schema
go test -race -tags=integration ./pkg/schema -count=1 -timeout=180s
```

后续仍需旧库升级/采用预检、显式CLI、启动只读验证、角色GRANT、失败向前修复与回退流程。旧版本AutoMigrate与新方案不可混跑后宣称受同一锁保护；这些接线完成之前，应用现有启动路径仍会自动DDL。本轮没有访问或迁移生产环境。

## 不可变新库基线

`internal/dbschema` 的版本1冻结58张表、34条外键和2条历史数据修复。执行包装源码与有序SQL共同参与checksum；未来变更只能新增版本，不能修改已发布v1。实际迁移不引用实时GORM模型，避免同一版本随模型变化重新解释。集成测试将独立空库执行后的完整表、列、索引和外键，与当前唯一模型注册表产生的结构逐项比较，同时比较两项数据修复的结果。仅无语义顺序的索引/约束排序规范化，列顺序保留。

基线只支持空库：在持有迁移锁的同一连接内再次检查，任何非ledger表或视图均拒绝。它不自动认领既有未版本化数据库，不解决升级或部分DDL回退。预检角色必须具备目标schema完整元数据可见性。当前验证MySQL8.4.11；未对生产数据执行。

```sh
go test -race -tags=integration ./internal/dbschema -count=1 -timeout=180s
```

显式初始化（例如通知时区登记）可复用 `WithMigrationLock` 与 `VerifyConnection`：在同一个物理连接先锁定、再验证账本与操作，避免单连接池再次取连接而死锁。锁获取仍为fail-fast，不暗中重试初始化写入；callback必须在返回前提交或回滚事务，panic会脱敏并丢弃物理会话，避免事务和锁泄漏。新测试验证单连接池内核验及panic后的再次获取锁。
