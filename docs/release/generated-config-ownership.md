# 生成配置的原子归属写保护

## 修复的触发条件

原流程在发布前检查元数据，随后按ID更新或删除。具有配置编辑权限的操作者若在两步之间通过真实更新接口修改名称、PoolID、类型或实例地址，发布器仍可能覆盖或删除已不归属自己的行。两条原始反例使用真实Gin handler/service/DAO和SQLite内存库复现，不依赖模拟DAO。

现在四个发布器在预检时复制不可变的预期归属值。生成器专用条件写入同时匹配ID、未删除状态、PoolID、配置类型、名称和实例地址；MySQL名称及地址使用字节比较，不能借默认不区分大小写或尾空格的列比较误认归属。普通配置CRUD接口及语义保持。

批量条件更新在数据库事务内完成，任一归属冲突回滚该批SQL更新。更新影响0行时，只有回读确认当前仍为目标归属且全部业务生成字段已等于desired，才判为幂等成功；缺失或不同归属返回固定冲突，不把0行直接视为成功。

退休先通过条件数据库删除闸门，再删除Redis内容，最后移除重试索引。删除0行仅在真实、相同归属的软删除记录仍存在，且没有同配置键的未删除替代行时可幂等；其它情况拒绝，等待重新预检。Status2的未删除custom/foreign行同样受保护；规范名称、PoolID等仍属本控制器的行不会仅因Status2变成外部所有者。

## AlertManager退役恢复

旧实例的规范AlertManager主配置行现在也会条件软删除，避免真实配置列表继续显示旧IP的Active生成物；底层软删除记录保留。自定义、他池和歧义配置不自动删除。

Webhook旧元数据条件退役后，若Redis删除失败，仅靠未删除元数据列表无法再次发现它。因此新增稳定PoolID的私有retirement intent集合，只存ID、PoolID、类型、名称、实例地址五个归属字段，不存配置正文或凭据。先完整验证意图，再可靠pending、登记意图、条件退役数据库、清理Redis、移除意图并确认SHA。

恢复同键desired时，先恢复可证明归属的新生成物，再取消旧意图；取消失败后再次关闭，可按同键归并旧tombstone与当前唯一规范owned行，先条件退役当前行后清理。覆盖不同ID重建、同ID合法更名、重复开关及Redis/索引故障；不能借此吞掉foreign/custom替代行或多个活跃行。

## 验证与范围

- 原两条HTTP+SQLite反例保持原预期并转绿；独立原始4个有效ABA场景、6个归属对照和1个同ID更名恢复场景race通过。早期把仅Status2变更误作foreign的预期已明确纠正，不将错误预期算作实现回归。
- 完整cache 703叶、DAO 23叶通过race；最终全Go test/vet、cache/DAO/utils/alert service/model/scrape service六包完整race、全标签只编译通过。没有用编译检查替代真实集成。
- 本机独立MySQL临时库和专属测试账号实际运行native测试，`clientFoundRows=false/true`两种模式均通过，零skip；验证大小写/尾空格字节匹配、完整no-op、合法更名、tombstone和替代行。SQLite另验证NOCASE列及事务回滚。没有访问演示数据或生产；临时库、账号和DSN文件已清理，私有测试日志保留。

SQL条件写入不等于跨数据库与Redis事务，也不保证多进程exactly-once。写前已观察到的归属冲突仍零写拒绝；预检后的竞争可能已经记录pending或成员，不能声称全部Redis写入为0。尚未预留的create-if-none键位竞争、池删除生命周期和全局调度不属于本次保证，没有借此宣称所有并发问题已解决。
