# 工单评论树完整性

评论创建接口保留既有合同：父评论存在且属于同一工单时，允许继续回复该父评论；并没有仅允许回复根评论的限制。评论内容、`parent_id`、`children` 的 JSON 类型、状态过滤、认证操作者、权限入口和事务通知事件均不变。

旧构造按创建时间升序将子评论的结构体值拷贝到父节点。当后续再给这个子评论追加孙节点时，已经拷贝的值仍持有空 `Children`，因此正常的三层/五层回复会在树响应中漏显。数据仍在数据库，不能将问题描述为数据库删除。

## 当前读取行为

构造先建立局部父子关系，再用叶节点队列迭代后序组装。子树完整后才复制到父节点；构造无递归，时间及额外空间为 O(N)，根和兄弟保留输入顺序。读取对相同 `created_at` 补 `id ASC` 次序，避免同一时间戳顺序不明确。`Children` 仍为原来的值切片，未改变模型或接口字段类型。

缺失父节点的评论不会被提升为根；这也保留了父节点被现有正常状态过滤排除时的既有显示行为。仅有孤儿时保留原 nil/null 根结果。循环、自引用或无效/重复节点身份会明确返回读取错误，而非无限递归或返回看似完整的部分树。没有修改、删除或截断任何数据库记录；平铺读取仍保留实际存储数据。此阶段不迁移或自动修复坏历史关系。

## 验证与边界

- 旧源码真实反例：DAO 三/五层按时间正序丢孙节点，倒序偶然通过；HTTP 认证操作者连续创建三层成功，平铺读取三条而树读取缺第三层。
- 修复回归覆盖三/五层、父子输入反序、兄弟/根顺序、同时间戳 ID 次序、缺父与状态过滤、循环拒绝、万层迭代构造和输入对象不变。
- 隔离 SQLite/httptest 使用实际 handler、service、DAO 和事务 outbox：创建三/五层后平铺/树均完整，伪造操作者和系统标志不能覆盖认证身份；跨工单 parent 拒绝，且不新增评论或通知事件。没有启动通知 worker 或实际发送消息。

测试入口为 `internal/workorder/dao/instance_comment_tree_test.go` 和 `internal/workorder/api/instance_comment_tree_http_test.go`。SQLite 不作为 MySQL 行锁或生产容量证明。本阶段仅修 Go 返回树完整性；前端后代展示独立交付，实例详情全量历史预加载和分页/容量治理也未在此阶段改变。不宣称任意深度 JSON 序列化或整页渲染已完成容量验收。
