# 采集池删除与关联定义保护

## D1：完整定义引用检查

删除采集池不再仅依赖服务层的启用job预检。最终DAO事务锁定未删除父池，检查全部未删除的采集任务、告警规则和录制规则，包含禁用定义；任何引用或查询错误都阻止软删除。没有自动删除用户定义，也不把同号AlertManager池当作Scrape池。

三类定义创建或迁移时，在自己的写事务内锁定并验证目标父池仍存在且未删除，再锁定或写入子行。删除与关联写使用同一父行锁协议，避免服务层先查后写留下并发孤儿。record更新省略PoolID时保留原有struct更新语义，并在锁内重检初读的关联没有被另一请求迁移。

本阶段没有添加数据库外键或改变schema，也不约束绕过DAO的手工SQL。服务层原启用job友好提示保留，权威检查在DAO；检查和删除失败均保留原数据。

## 验证

新增7个主测试、27个子场景及原有目标包测试通过，覆盖三类启用/禁用引用、缺失或已删父池、迁移和省略关联、查询错误回滚及真实删除handler拒绝。旧实现对照保持可编译并出现明确业务断言失败，无nil依赖panic充当红例。

独立4个内存race场景验证省略关联的竞争迁移检测和三类父查询后的取消传播；SQLite仅证明事务连接及锁子句，不能冒充MySQL行锁。

另在专属本机MySQL临时库实际执行6个锁先后场景：job、alert、record各自的创建先行与删除先行，全部通过且零skip。没有触碰演示数据，临时库、专属账号和DSN随后清理。最终全Go test/vet、相关包完整race、全标签只编译通过。

## 仍需D2闭环

D1不代表池删除生命周期全部完成：没有定义但仍有生成配置时的清退，以及历史软删除池的残留配置，仍需显式删除意图或可验证tombstone驱动的可重试退役。不能把普通库存缺失、读取失败或日志中的异步失败当作已清理成功。D2尚未交付，本阶段没有修改四个发布器、配置CAS或全局生成开关，也未上线。
