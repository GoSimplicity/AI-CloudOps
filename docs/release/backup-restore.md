# MySQL 备份恢复验收

使用本轮 Compose 中健康的 `cloudops/mysql` 服务，在随机独立数据库恢复备份，不覆盖现有 `cloudops` 业务数据库。需要 Docker CLI 及当前容器管理权限，不需要在宿主机提供数据库密码

```sh
python3 scripts/release-restore-check.py deploy/release/backups.local/20261023T035342Z/mysql.sql
```

工具支持 `--container cloudops-mysql-1` 与 `--timeout 120`。只有 Compose 标签为 `cloudops/mysql` 且健康的容器可通过检查；单次容器操作及导入期限限定在 1–3600 秒

验收分为以下步骤：

1. 只读获取当前可信 `cloudops` 的表、列、索引、外键结构指纹，以及唯一未删除管理员关键字段、有效 API 权限目录指纹
2. 生成随机数据库、临时 SQL 用户和密码，确认名称未被占用。临时用户只拥有该数据库上的建表、数据恢复及必要索引、视图、触发器权限，无全局权限、FILE 权限或授权权
3. 使用容器系统 `mysql` 用户及临时 SQL 用户流式导入，禁用客户端本地命令与 `LOCAL INFILE`，丢弃不可信 SQL 的所有输出。密码通过容器已有环境变量或标准输入传入，不进入命令行参数或日志
4. 用同一限权用户核对恢复结构和关键数据，不以 root 查询不可信恢复对象。root 只运行工具构造的可信源库只读及临时资源管理 SQL
5. 成功、恢复失败或超时均进入清理：终止该临时用户会话，删除本次独立数据库与用户，并核对资源已消失。清理失败返回非零并仅指出本次生成的资源名称，需恢复容器访问后清理这些名称

工具不会读取、恢复或输出同目录的 `deployment.env`。它含生产凭据与加密密钥，应继续按私钥材料保存，不能提交 Git。验收也不包含 Redis 队列、AIOps 上传文档、外部集群或云资源恢复

当前数据库仅作为可信基线。历史快照与现库结构或关键数据有正常变化时，工具会明确失败；应选择匹配版本的可信基线重新验收，不能通过跳过校验或扩大临时用户权限处理。包含跨库 `USE`、全局 GTID 操作、外部 `DEFINER`、存储例程或事件权限需求的备份也会保持失败，本工具不自动申请这些权限。请使用 `release-backup.py` 生成单库备份

本次真实隔离验收使用 MySQL 8.4.11 容器和 `20261023T035342Z/mysql.sql`：

- 连续三次恢复均匹配 46 张表结构、管理员及有效权限目录，重复执行无名称或对象冲突
- 不可信 SQL 读取 `mysql.user` 被拒绝，客户端本地 shell 命令未执行，探测文件不存在
- 拒绝用例前后，业务库结构与关键数据指纹一致，`restore_` 前缀临时数据库及用户均为零

工具回归只使用临时文件、替身与内存，不依赖 Docker：

```sh
python3 -m unittest discover -s scripts/tests -p test_restore_check.py -v
python3 -O -m unittest discover -s scripts/tests -p test_restore_check.py -v
```

覆盖成功、空备份、创建/导入失败、结构/关键数据不一致、随机资源清理、名称碰撞及任意名称拒绝、会话清理竞争、删除步骤部分失败、其他容器拒绝、密码仅进入标准输入与错误信息隐藏
