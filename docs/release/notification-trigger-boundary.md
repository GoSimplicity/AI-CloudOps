# 1.0 通知触发边界

> 当前口径（2026-10-30）：本页早期只开放 immediate 的限制已经由持久事件与调度引擎阶段扩展。完整状态见[当前完成度矩阵](readiness-current.md)；下文区分当前入口与保留的历史兼容门禁。

当前创建和更新支持经过严格校验的 immediate、delayed、scheduled、conditional，以及有明确次数和间隔的重复通知。delayed 必须提供有效延迟，scheduled 客户端输入要求明确 UTC 时间，conditional 只接受规定字段与数值；未知类型、缺字段或互斥参数会被拒绝。可靠事件 worker 保存计划、按到期时间调度、只在已确认成功后创建下一次重复，并支持取消和有界重放；不会把保存成功当作已经投递。实现与回归见 `internal/workorder/service/notification_validation.go`、`notification_event_worker.go`、`notification_schedule_test.go` 和隔离 MySQL 调度测试。

历史未经过当前版本校验的高级配置不会因为读取、修改普通元数据或重复点启用就被激活。操作者必须显式补全/调整触发配置并重新验证，建立当前 trigger_version；也可禁用或明确转为合法即时配置。旧的直接发送辅助路径仍只接受简单即时配置，拒绝高级触发进入该路径，防止绕过调度提前发送；高级触发交由可靠事件 worker 处理。

手动测试发送仍是操作者明确选择配置、通道与地址后的一次独立动作，不证明该配置的调度、重复或取消已经验收。邮件/飞书应用通道、部门/custom接收人与逐通道去重继续有效；站内 `in_app` 使用按用户隔离的消息与同事务投递账本，见[站内消息合同](notification-inbox.md)。AIOps飞书自定义机器人使用独立服务端webhook配置，不与工单应用ID收件人混用。

历史阶段验证曾先红覆盖非即时/未知类型的误接受、历史配置激活和直接发送门禁，随后workorder全模块race通过。后续调度阶段新增合法高级触发、延迟不提前发送、条件跳过、确认后重复、重复计划持久化失败恢复、取消及并发 MySQL 回归。既有真实本机HTTP飞书应用替身收件箱继续验证部门/custom去重、禁用用户排除与上游失败传播；这些隔离证据不代表真实邮件/飞书已经实投，当前阶段不发送到外部。

历史 immediate 若残留不合法或未验证的高级参数，仍不能仅改类型或点启用绕过。更新会合并现存参数后完整校验；明确清除触发字段的入口和 trigger_version 共同管理当前配置，合法、有次数限制的即时重复由事件 worker 执行。详细来源与旧记录兼容证据见 [notification-scope.md](notification-scope.md)，其中早期“只支持即时”的阶段描述不覆盖当前高级调度合同。
